## 2. Specific Questions for Legal Counsel

### A. Specific Files and Acquisition Method of Minecraft Data
1. The working copy contains:
   - `RadCore/data/mc777/{blocks,entities,items,menus,PROVENANCE}.json` (`_provenance`: `vineflower-direct`, `reports/registries.json#minecraft:block`);
   - `RadCore/src/mc777_data.rs` (generated by `scripts/generate_mc777_data.ps1`);
   - `RadCore/src/packet/configuration_static_tags.rs` (`// Auto-extracted from Minecraft Java 26.3 vanilla data tags.`);
   - `RadCore/src/packet/configuration_core_tags.rs` (`// Extracted from installed client data; no game code or asset payloads.`).
2. **Separate questions for each action (acquisition → transformation → usage → distribution):**
   - **Acquisition:** Is it permissible to extract numeric IDs of blocks/items/entities/menus and tag lists from the official Minecraft 26.3 server/client or via tools such as data generator / `vineflower`?
   - **Transformation:** Does transforming JSON into Rust structs (`mc777_data.rs`) or an external package `versions/26.3/data/*.json` alter its legal status?
   - **Usage:** Is local usage permissible for protocol interoperability?
   - **Distribution:** Is distributing these tables in a public GitHub repository permissible (under `MIT OR Apache-2.0` or under a separate `assets/NOTICE.md`), or is the only permissible approach requiring the end user to generate/provide the data package locally?

### B. Authorship, Absence of `.git`, and Clean-Room Limitations
1. The directory lacks `.git`, so there is no commit history, DCO/CLA, or contributor verification (all 400+ proprietary files carry `UNKNOWN` status).
2. **Question:** What documentation (rights holder confirmation, contributors' agreement, provenance/creation history) is required prior to the first public commit under `MIT OR Apache-2.0`?
3. Current developers and AI sessions already had access to `mc777` tables and `Paper-26.3/` (local reference). Is a formal clean-room rewrite required for specific modules (e.g., `RadVersions/v26_3` physics/simulation/worldgen), or is a legal evaluation of the proprietary code sufficient?

### C. Third-Party Licenses and Dependencies
1. In `Cargo.lock`, 246 crates declared permissive licenses (`MIT`, `Apache-2.0`, `BSD-2/3-Clause`, `ISC`, `Zlib`, `Unicode-3.0`, `Unlicense`, `CDLA-Permissive-2.0`, `BSL-1.0`) and 1 disjunctive license `r-efi` (`MIT OR Apache-2.0 OR LGPL-2.1-or-later`).
2. **Question:** Which specific notices (`LICENSE-MIT`, `LICENSE-APACHE`, consolidated `NOTICE` for `Apache-2.0`/`BSD`/`Unicode-3.0`) are mandatory for:
   - publishing a **source release** on GitHub;
   - publishing a **binary release** (`rad-server.exe`, `rad-proxy.exe`, `rad-limbo.exe`, `rad_version_26_3.dll`)?
3. Confirm whether rejecting `Pumpkin` (`GPL-3.0`), `SteelMC` (`AGPL-3.0-or-later`), and `crab_nbt` (`GPL-3.0`) is the correct decision, and whether any undesirable licensing implications arise from the plugin/WASM format (`RadAPI` + `wasmi` under `Apache-2.0 OR MIT`).

### D. Branding, EULA, Jurisdictions, and Commercial Use
1. In [README.md](../../README.md), there is a disclaimer: `NOT AN OFFICIAL MINECRAFT PRODUCT. NOT APPROVED BY OR ASSOCIATED WITH MOJANG OR MICROSOFT.` Is this phrasing sufficient under the Minecraft Usage Guidelines, and where else should it be placed (in the `rad-server` CLI banner, GitHub Releases page, crate descriptions)?
2. **Jurisdictions and commercial use:** What limitations apply in the US, EU, and Ukraine regarding protocol reverse engineering for interoperability (interoperability exceptions, e.g., EU Software Directive / DMCA §1201(f)), and does the assessment change if the project or derivative products are used commercially (hosting, paid servers, paid plugins)?
